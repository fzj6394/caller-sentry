# 归属地可见性 与 来电显示延迟 · 分析报告

> v2.2 / 2026-11-18　设备：三星 SM-S9360（港版 S25，One UI 9 / Android 17）
> 本文所有耗时数据来自本机对真实文件的测量（PC，热缓存），真机冷态约 ×4~10。

---

## 一、问题原因：为什么三星「电话」的通话记录里没有归属地

### 1.1 我们做了什么

v2.2 已实现官方通道 `CallerIdProvider`（Directory Provider，虚拟号码目录）：

- authority：`cn.fzj.callersentry.directory`
- manifest：`exported=true` + `readPermission=BIND_DIRECTORY_SEARCH` + `meta-data android.content.ContactDirectory=true`
- 实现：`/directories` 返回目录登记行；`/phone_lookup/<number>` 返回 `DISPLAY_NAME`
- 取标签顺序：号码库精确 → 黄页 → 号段规则 → 在线缓存 → 归属地

`aapt dump xmltree` 已确认 provider 与 meta-data 都进了包，dex 含 `CallerIdProvider`。

### 1.2 为什么还是不显示

| 编号 | 原因 | 性质 |
|---|---|---|
| R1 | **Directory 是"被动应答"机制**：只有拨号器主动来问，我们才有机会给名字。三星「电话」用自家识别服务，不查第三方目录 → 没人问，provider 就永远不被调用 | 根因，不可控 |
| R2 | 通话记录里的姓名是**派生字段**：ContactsProvider 用通讯录的 `cached name` 填充。第三方 `update()` CallLog 会被拒或静默忽略，即使拿到 `WRITE_CALL_LOG` 也改不了 name 列 | 系统限制，无解 |
| R3 | Android 16（API 36）起，实现目录的 App 必须持 `READ_CALL_LOG`，否则 ContactsProvider 不转发查询。我们 targetSdk 34 可能被豁免，但已声明并在「拦截记录与诊断」里让用户授权 | 附加门槛 |
| R4 | 部分 ROM 只在**来电界面**用目录结果，**通话记录列表**不查 | 厂商差异 |

**判断：这条路只能"等拨号器来问"，我们不能主动推送，因此不可依赖。** 需要把可见性做在别的位置。

## 二、替代方案（不依赖通话记录界面）

按"确定有效 → 有条件有效"排序，均给出触发时机、展示位置、实现落点。

### A. 通话中常驻通知 + 通话结束回执（P0，100% 可控）

| 项 | 内容 |
|---|---|
| 触发 | `onScreenCall` 里 respond 之后立即 post 一条 `ongoing` 通知 |
| 展示 | 通知栏常驻「顺丰速运·快递 / 95338」，通话界面下拉即可见；通话结束后改为「刚才 95338 顺丰速运·快递 · 未接 0:12」 |
| 落点 | `ScreeningService.show()` 扩展；新建 `CallEndWatcher`（用 `ContentObserver` 监听 `CallLog.Calls` 新增，或 `Notification.timeoutAfter` 兜底） |
| 成本 | 中（约 100 行）；不需新权限 |
| 局限 | 来电全屏时通知区必须下拉才看到，不能替代悬浮条 |

### B. 通话结束回执通知带动作（P1）

- 内容：「刚才 138**** 绍兴 · 电信 · 号码库已标记」，两个动作按钮：**回拨** / **加入号码库**
- 落点：`PendingIntent` + `BroadcastReceiver`，复用 `LogStore`
- 价值：不打断通话、可回溯、可一键把号码加库（把"被动挨打"变成"主动积累"）

### C. 桌面小部件：最近 3 通来电（P1）

- 每行：时间 · 号码 · 归属地 · 标记（颜色区分拦截/提示）
- 落点：`AppWidgetProvider` + `RemoteViews`，数据源 `LogStore.all()`
- 局限：RemoteViews 只能用系统控件，样式朴素；三星桌面允许多尺寸

### D. App 快捷方式 + 剪贴板速查（P1，成本最低）

- 长按图标 →「查号」直达输入框（`res/xml/shortcuts.xml`）
- 进入 App 时若剪贴板是号码，自动填入并查询（`ClipboardManager`，只在 App 前台读，不外传）
- 场景：别人报号码、短信号码，复制即查

### E. 导出 vCard 导入通讯录（P2，唯一能"顺带"出现在通话记录里的办法）

- 把黄页 79 条 + 自己标记的号码生成 `.vcf`（`ORG=顺丰速运`，`NOTE=黄页·快递`），导入到**单独分组**
- 效果：通话记录、来电界面、短信会话全部显示名字——因为走的是通讯录，不是目录
- 代价：写通讯录（可一键删除该分组）；**只覆盖已知号码**，陌生号码仍只有号码
- 落点：`SourcesActivity` 加「导出黄页为联系人」按钮，用 `ACTION_SEND` 发出 vcf 文件

### F. 运营商侧：让电话不响（P2）

- 导出号码/号段清单（txt/csv），手动导入移动「高频骚扰电话防护」/ 联通管家 / 天翼防骚扰
- 效果：运营商侧直接拦截，不需要任何界面显示
- 落点：`RulesActivity` 导出按钮已有，补一个"运营商格式"

### G. 明确不推荐

`AccessibilityService` 读通话界面后叠加文字：侵入性强、耗电、隐私风险、易被系统杀，且与 Play 政策冲突。仅当悬浮窗被三星彻底禁用、且用户明确要求时才考虑。

## 三、来电显示延迟：原因拆解与优化

### 3.1 实测数据（PC，热缓存）

| 环节 | 实测 | 真机冷态估算 |
|---|---|---|
| `phone.dat` 解压 + 读入（4,484,792 字节，APK 内 deflate 1,151,813 字节） | **15.5 ms** | 60 – 200 ms |
| `new PhoneLookup(bytes)` 索引解析（497,191 条） | **0.11 ms** | 0.5 – 2 ms |
| 单次号码查询（19 次二分） | **0.4 µs** | 2 – 5 µs |
| 60,000 次查询总耗时 | 22 ms | — |

**结论：归属地计算是微秒级，可以完全忽略。延迟来自"加载 / IO / 排队 / 我们自己的时序设计"。**

### 3.2 现状时序（v2.2）

```
onScreenCall 进入
  ├─ 读 SharedPreferences 7~9 次（首次会解析整个 XML）
  ├─ 黄页 HashMap 命中（O(1)，微秒）
  ├─ Blacklist.load() × 2（getStringSet 会拷贝集合 + 排序）
  ├─ MarkCache.get（内存 Map，微秒）
  ├─ 判断三档 / 重复来电
  ├─ respondToCall   ← 系统在这之后才推来电界面
  ├─ PhoneLookup.get() 取归属地（若冷启动在此处加载 4.3MB）
  ├─ LogStore.add（同步触发 SP 整份序列化）
  └─ Overlay.show → post 到主线程 addView（此时主线程在做来电动画）
```

### 3.3 可能原因（按概率排序）

| # | 原因 | 证据/机理 | 影响量级 |
|---|---|---|---|
| C1 | **冷启动 + 首次加载 asset**：进程被来电拉起，`Application.onCreate` 的 warmup 线程与 `onScreenCall` 抢同一把锁（`PhoneLookup.get` 是 `synchronized`） | 代码事实：`synchronized static get()`；warmup 在 `App.onCreate` 启动 | 100 – 300 ms |
| C2 | **SharedPreferences 首次解析 + 多次读取**：来电路径上调 `Prefs.sp` 7~9 次，首次要解析 XML | 代码事实：`blockMode` / `repeatMinutes`×2 / `onlineOn` / `overlayOn` / `notifyOn` / `remember` | 20 – 80 ms |
| C3 | **日志同步落盘**：`LogStore.add` 里 `getString` + `split` + `edit().apply()`，apply 的序列化在后台但会在主线程路径上排队 | 代码事实：`LogStore.add` 在 respond 之后、同线程执行 | 10 – 40 ms |
| C4 | **overlay 在 respond 之后才发**，且 `addView` 排主线程队（来电动画期间主线程繁忙） | 设计使然 + 主线程竞争 | 50 – 300 ms |
| C5 | **通知在来电全屏界面被抑制**：只在通知栏可见，全屏来电时看不到 | 系统行为 | 感知为"没显示" |
| C6 | 在线查询若缓存未命中且**同步等待**（v2.1 之前的实现） | 已在 v2.1 改为异步 | 0（已修） |
| C7 | 三星电池策略延迟拉起服务（首次冷启更明显） | 需把 App 电池设为"不受限制" | 不定 |

### 3.4 优化方向（含预期收益与风险）

| 编号 | 优化 | 做法 | 预期收益 | 风险 |
|---|---|---|---|---|
| O1 | **去掉锁等待** | `PhoneLookup` 静态引用改 `volatile`，加载完成后才赋值；`onScreenCall` 读到 `null` 就跳过归属地（fail-open），由 warmup 后台填充并触发下次生效 | 消除首通 100 – 300 ms | 极低；仅首通可能没有归属地 |
| O2 | **设置快照** | App 里维护 `Settings` 快照（mode / repeat / online / overlay / notify / url），SP 变更时同步；来电路径零 SP 读 | 20 – 60 ms | 低，需保证写路径都更新快照 |
| O3 | **日志异步** | `LogStore.add` 改为单线程 `Executor` 入队即返回 | 10 – 40 ms | 低；进程被杀可能丢最后一条 |
| O4 | **视觉提前** | respond **之前**先 post 悬浮条（只显示号码），算出归属地后 `setText` 补齐 | 感知延迟从"等"变"逐步补齐" | 低；需保证不早于拦截判定 |
| O5 | **overlay 独立 Looper** | 用 `HandlerThread` + 它的 Looper `addView`，不排主线程队 | 50 – 200 ms | 中；需自己管理线程生命周期 |
| O6 | **asset 不压缩 + mmap** | `aapt2 link -0 dat`；`getAssets().openFd()` 拿 FD → `MappedByteBuffer`，零解压零堆拷贝 | 首次加载 ≈ 0 | APK +3.3 MB（1.4 → 4.7 MB） |
| O7 | **预建 NotificationChannel** | `App.onCreate` 建一次，`ScreeningService.show` 不再每次 create | 5 – 20 ms | 无 |

### 3.5 验证要点（可落地，无需电脑）

**V1 内置分段计时（最重要）**
在 `onScreenCall` 打 5 个时间戳：进入 / 本地判定完成 / respond 完成 / 归属地完成 / overlay 已添加。写入新表（或 `LogStore` 附加字段），在「拦截记录与诊断」显示最近 5 通的分段耗时。这样你能直接在手机上看数字，不用 adb。

**V2 对比矩阵**

| 场景 | 观察点 | 期望 |
|---|---|---|
| 重启手机后第一通 | 悬浮条出现时间 | < 400 ms |
| 紧接着第二通 | 同上 | < 150 ms |
| 关掉在线查询 | 同上 | 无变化（证明异步已生效） |
| 关掉悬浮窗只用通知 | 通知是否被全屏来电抑制 | 需下拉才见即符合预期 |
| 飞行模式 | 归属地仍显示 | 是 |

**V3 验收指标**
- respond 间隔 < 50 ms（本地判定 + 三档计算）
- 悬浮条出现：冷 < 400 ms，热 < 150 ms
- 归属地文字补齐：冷 < 600 ms
- 若 O2/O3 落地后仍未达标，再看 O5/O6

**V4 有电脑时的补充**
`adb logcat -s CallSentry`（需先加日志 Tag）；`adb shell dumpsys notification --noredact | grep callersentry` 看通知是否被系统抑制。

## 四、优先级与注意事项

### 4.1 优先级

| 级别 | 内容 | 理由 |
|---|---|---|
| **P0** | O1 去锁、O2 设置快照、O3 日志异步 | 纯代码、零权限、合计减少 130 – 400 ms，风险最低 |
| **P1** | O4 视觉提前、O7 预建通道、A 通话中常驻通知、B 结束回执带动作 | 直接改善"看得见"这个核心诉求 |
| **P2** | C 桌面小部件、D 快捷方式+剪贴板、O5 独立 Looper、E vCard 导出 | 增益明确但成本上升 |
| **P3** | O6 mmap、F 运营商清单 | 有明确代价（APK 体积 / 手工操作） |
| **不做** | G 无障碍服务 | 侵入性与隐私代价高于收益 |

### 4.2 注意事项

1. **提前 respond 不能牺牲拦截判定**：拒接/静音必须在 `respondToCall` 之前算完（现状如此），O4 只提前"画提示"，不改判定顺序。
2. **fail-open 原则**：任何加载失败、权限缺失、网络异常，一律放行来电，宁可少显示不可漏接。
3. **`READ_CALL_LOG` 敏感**：只在用户主动点按钮时申请，拒绝后不反复弹。
4. **Directory Provider 保留但不再投入**：它不影响其他功能，万一将来三星支持就自动生效。
5. **数据准确性边界**：号段只到市，携号转网后运营商不准；UI 文案不要说得比实际更准。
6. **三星电池策略**：App 需设为"不受限制"，否则悬浮条/通知会被杀，任何代码优化都白费。
7. **不要用"提前 respond + 事后拒接"**：一旦 respond 放行，就无法再拒接，顺序不能反。
